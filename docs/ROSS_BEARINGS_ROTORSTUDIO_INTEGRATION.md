## Implemented integration slice

### Native hydrodynamic implementation progress

The standalone Fortran bearing engine now also contains source-faithful
building blocks from the current ROSS fluid-film implementation:

- fixed-geometry translators for PartialArc, Elliptical, OffsetHalves,
  MultiLobe, PressureDam and PlainJournal;
- TiltingPad configuration validation and ROSS-compatible initial-position
  mapping;
- the Allaire Q4 Reynolds element matrix/source kernel;
- ROSS banded Reynolds assembly/LU/cavitating back-substitution kernels;
- the rigid/isoviscous baseline film-thickness kernel used as the next
  TiltingPad/PlainJournal native-solver layer.

These are qualified as implementation sub-gates only. They do **not** yet
constitute the complete native PlainJournal/TiltingPad operating-point solver:
pressure-field orchestration, journal/pad equilibrium, perturbation fields,
pad-DOF condensation and THD/TEHD remain open.


The RotorStudio solver can now consume two complementary advanced-bearing
paths without changing the frozen legacy type 1–8 / 20 implementation.

### Native Fortran bearing physics

`libdrmbearings` exposes a C ABI for:

- `BallBearing`;
- `RollerBearing`;
- `CylindricalBearing` (ROSS simplified analytical short-bearing model);
- `SqueezeFilmDamper` with `groove`, `end_seals`, and
  `groove-end_seals`;
- ROSS-style 1-D and 2-D coefficient interpolation.

The Python Core loads this library independently from `libdrmrotor`.  The
rotor solver does not depend on ROSS Python at runtime.

### Coefficient-provider hydrodynamic families

The following typed RotorStudio objects are accepted through solved
ROSS-style coefficient tables:

- `PlainJournalBearing`;
- `PartialArcBearing`;
- `EllipticalBearing`;
- `OffsetHalvesBearing`;
- `MultiLobeBearing`;
- `PressureDamBearing`;
- `TiltingPadBearing`;
- generic `CoefficientBearing`.

This is a numerical integration contract, not a claim that the full ROSS
THD/TEHD operating-point solver has already been ported.  A TiltingPad table
may therefore be generated by a qualified external/native bearing solver and
then consumed by RotorStudio with its spin-speed and whirl-frequency axes
preserved.

## Axis contract

Every advanced coefficient provider is evaluated as

```text
M_b, C_b, K_b = B(Omega_rotor, omega_excitation)
```

Synchronous modal/response analyses use
`omega_excitation = Omega_rotor`.

General auxiliary/foundation FRF paths keep the two values separate and
re-evaluate the advanced bearing at every excitation-frequency point.

Supported coefficient representations:

- constant;
- speed-only 1-D;
- excitation-frequency-only 1-D;
- speed x excitation-frequency 2-D;
- PCHIP with ROSS endpoint extrapolation;
- piecewise linear interpolation.

## Rotor assembly bridge

For the current qualified lateral 4-DOF RotorStudio assembly, an advanced
radial bearing is evaluated first and its 2x2 translational K/C is mapped to
the existing qualified legacy type-5 assembly row:

```text
advanced bearing
      |
      v
libdrmbearings
      |
      v
Kxx Kxy Kyx Kyy / Cxx Cxy Cyx Cyy
      |
      v
temporary legacy type-5 row at the requested (Omega, omega)
      |
      v
existing libdrmrotor assembly / eigensystem / response
```

This is intentionally an adapter.  Existing project bearings are not
rewritten and the type 1–8 / 20 code path is untouched.

A nonzero advanced bearing mass matrix is rejected rather than silently
discarded because the current legacy type-5 bridge has no bearing-mass
contract.

## Analyses enabled in this slice

- stationary modal / eigensystem;
- matrix assembly at a specified speed;
- synchronous frequency response with bearing re-evaluation per speed;
- auxiliary FRF with independent rotor speed and excitation frequency;
- foundation FRF with independent rotor speed and excitation frequency;
- iterative critical speeds using repeated advanced-bearing modal evaluation;
- direct bearing K/C evaluation through `SolverFacade.advanced_bearing()`.

## Explicitly blocked until separately qualified

- full native PlainJournal THD/TEHD solve;
- full native TiltingPad equilibrium, perturbation and pad-DOF condensation;
- native ThrustPad;
- axial coupling of ThrustPad into the lateral 4-DOF rotor;
- advanced-bearing run-up and transient time integration;
- coaxial advanced-bearing assembly;
- rotating-frame/asymmetric advanced-bearing assembly;
- advanced bearing mass terms.

The blocks are explicit exceptions, not silent constant-coefficient
substitutions.

## Domain and persistence

`RotorModel.advanced_bearings` stores typed advanced bearings in parallel
with the original `RotorModel.bearings`.

Project schema version 2 persists:

- bearing family;
- physical/native inputs;
- coefficient axes and tables;
- interpolation mode;
- provenance dictionary.

Schema-1 projects remain loadable because the advanced-bearing payload is
optional.

## Qualification

The dedicated workflow keeps the existing frozen Stage-1 collection at
exactly 57 tests and runs the new bearing qualification separately.

The integration tests now cover native Ball/Roller/Cylindrical/SFD oracles,
fixed-geometry and TiltingPad configuration ABI, the Reynolds Q4 kernel,
independent spin/whirl interpolation for a TiltingPad coefficient grid,
exact collapse of a constant advanced bearing to the legacy type-5 modal
path, speed-dependent bearing re-evaluation at every synchronous FRF point,
and save/reopen of a typed TiltingPad coefficient model with provenance.

No family should be labelled `NATIVE_TEHD_QUALIFIED` until its remaining
standalone bearing-physics gates are implemented and compared to the frozen
ROSS authority.
